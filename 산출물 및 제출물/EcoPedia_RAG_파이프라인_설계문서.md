## 1 설계 목적과 범위

EcoPedia는 국내 멸종위기 야생생물 282종의 기본 정보와 외부 문서를 함께 검색하여 종별 질문과 두 종 생태 비교에 답하는 서비스이다. RAG는 답변 전에 관련 문서를 검색하고 그 근거를 생성 모델에 제공하는 방식이다. 학습된 모델 지식만으로 생태·분포·위협 정보를 단정하지 않고, 사용자가 원문을 확인할 수 있도록 설계했다.

기본 목록은 2022-12-09 개정 기준이며 현재 법정 목록과 전수 대조하지 않았다. 원본에 없는 서식 환경·국내 분포·위협 요인은 빈 값으로 보존한다. 외부 생태정보는 출처를 가진 별도 근거로 추가하며, 미확보 속성을 임의로 채우지 않는다.

## 2 전체 구조

### 2.1 구성 요소와 역할

| 구성 | 구현 파일 | 책임 |
|---|---|---|
| 데이터와 설정 | ecopedia/catalog.py, ecopedia/config.py, data/species.json, config.json | 종 데이터·검색 텍스트·입력 정규화·설정 검증 |
| 문서 출처와 캐시 | ecopedia/sources.py | 위키백과 API 연결, 원문 수집, SQLite 영속 캐시 |
| 수집 제어 | ecopedia/ingestion.py | 검색어 추출, 후보 선별, 자체 문서 우선 처리, 로컬 문서 수입 |
| 벡터 저장소 | ecopedia/store.py | 두 컬렉션, 임베딩, 청킹, 검색, 중복 제거 |
| 모델과 프롬프트 | ecopedia/llm.py, ecopedia/prompts.py | JSON Schema 출력과 모델 호출 |
| RAG 그래프 | ecopedia/rag.py | retrieve·generate 노드, 근거 번호와 인용 검증 |
| 서비스 | ecopedia/service.py | 수집 후 그래프 실행, 조건 탐색, 처리 시간·안내 결합 |
| 생태정보 보강 | ecopedia/ecology.py, ecopedia/coverage.py | 종 일치·원문 대조, 발췌 저장, 정보 확보 상태 |
| 화면 | app.py, ecopedia/ui.py | 종 선택, 채팅, 비교, 조건 탐색, 근거와 진행 상태 표시 |

### 2.2 전체 흐름

```text
초기 준비
종 목록 JSON → 종별 검색 텍스트 → 임베딩 → species_meta

종별 질문 또는 두 종 비교
종 ID와 질문
  → 종 메타데이터 색인 여부 확인
  → auto_collect=true일 때 수집 단계 실행
      검색어 추출 → 자체 문서 확인 및 후보 검색 → 후보 선별
      → 본문 캐시 저장 → 청킹·임베딩 → species_docs
      → 저장된 종 자체 문서의 생태정보 발췌·원문 대조·파생 색인
  → LangGraph 시작
      retrieve → generate
  → 인용 검증 결과·실제 사용 근거·처리 시간 표시
```

문서 수집은 그래프의 세 번째 노드가 아니라 `EcoService.answer()`에서 그래프 실행 전에 수행한다. 따라서 필수 그래프 자체는 `START → retrieve → generate → END`의 두 노드 구조를 유지한다. `auto_collect=false`이면 질문 시 수집·생태 추가 추출을 생략하고 저장된 색인으로 답한다.

### 2.3 실행 모델과 저장소

| 항목 | 적용 |
|---|---|
| 생성 모델 | GMS OpenAI 호환 API / gpt-5.4-mini |
| 임베딩 모델 | text-embedding-3-small |
| 생성 설정 | temperature=0, 기본 타임아웃 60초, SDK 재시도 2회 |
| Vector DB | ChromaDB 영속 저장, cosine 거리 기반 컬렉션 |
| 벡터 저장 위치 | runtime/chroma |
| 수집·추출 캐시 | runtime/source-cache.sqlite3 |
| 설정과 비밀값 | config.json 및 환경변수. 실제 키·연락처는 문서와 제출 소스에서 제외 |

생성 모델은 문장을 만드는 역할, 임베딩 모델은 검색 벡터를 만드는 역할로 구분했다. gpt-5.4-mini로 변경할 때는 임베딩을 유지했으므로 기존 벡터를 다시 만들 필요가 없었다. 임베딩 모델·서버가 달라지면 `index-profile.json` 검사를 통해 기존 색인과 섞이지 않게 하고 별도 색인을 요구한다.

## 3 두 컬렉션과 메타데이터 설계

### 3.1 컬렉션 분리 이유

| 컬렉션 | 저장 단위 | 주요 목적 | 식별자 |
|---|---|---|---|
| species_meta | 종 1건당 기본 텍스트 1개 | 기본 사실·등급·분류군 검색, 선택 종 근거 강제 포함 | meta:{species_id} |
| species_docs | 외부 문서의 청크 | 생태 설명 검색, 출처·리비전 보존 | doc:{species_id}:{document_id}:{순번} |

짧고 구조화된 종 목록과 길이가 다른 외부 설명문을 분리했다. 두 자료를 하나의 컬렉션에 섞으면 짧은 메타데이터가 긴 설명문에 밀려 선택 종의 기본 사실이 검색 결과에서 빠질 수 있다. 메타데이터는 고정 ID로 직접 조회하여 강제로 포함하고, 외부 문서는 질문과의 유사도로 검색한다.

생태정보 발췌도 외부 원문에서 파생된 근거이므로 `species_docs`에 저장한다. `record_kind=ecology_fact`로 구분하며 세 번째 벡터 컬렉션을 만들지 않았다. SQLite는 벡터 컬렉션이 아니라 재수집·재추출을 줄이는 저장소이다.

### 3.2 종 메타데이터 컬렉션

검색 텍스트는 국명·학명·분류군·멸종위기 등급·국내 분포·서식 환경·주요 위협 요인·기준일을 한 문서로 묶는다. 없는 생태 속성은 ‘확인된 정보 없음’으로 표현한다.

| 필드 | 형식 또는 예시 | 용도 |
|---|---|---|
| species_id | 문자열, sp_0001 형태 | 종 식별 및 컬렉션 간 연결 |
| korean_name | 국명 | 표시·질문 문맥 |
| scientific_name | 학명 | 종 식별과 문서 검토 |
| taxon_group | 포유류 등 문자열 | 조건 검색의 정확 필터 |
| endangered_grade | 정수 1 또는 2 | 법정 등급 필터. 로마숫자 입력은 숫자로 정규화 |
| source_url | 원본 목록 URL | 출처 표시 |
| source_basis_date | 2022-12-09 | 자료 기준일 표시 |
| source_type | metadata | 외부 문서와 유형 구분 |
| document_title | 종명 + 종 메타데이터 | 근거 제목 |
| chunk_id | meta:{species_id} | 재색인 중복 방지 |

원본 분류군인 ‘양서파충류’ 등을 임의로 세분하지 않는다. 법정 등급과 IUCN·국가적색목록 등급도 서로 다른 지표로 취급한다.

### 3.3 외부 문서 컬렉션

| 필드 | 형식 또는 값 | 용도 |
|---|---|---|
| species_id | 종 ID | 해당 종으로 검색 범위를 제한 |
| document_id | ko-wiki-문서번호, en-wiki-문서번호 또는 manifest 지정값 | 원본 문서 식별 |
| document_title | 원문 제목 | 근거 표시 |
| source_type | web / pdf / text | 수집 출처 유형 구분 |
| source_url | 원문 URL | 사용자가 원문을 확인하는 링크 |
| source_file | 로컬 파일명 또는 빈 값 | PDF·TXT 원본 식별 |
| license | 이용 조건 문자열 | 출처 이용 조건 표시 |
| collected_at | ISO 형식 시각 | 수집 이력 |
| revision_id | 위키백과 리비전 문자열 | 수집 버전 식별 |
| search_query | 수집 검색어 | 수집 경로 추적 |
| chunk_id | 종 ID·문서 ID·순번 결합 | 항목별 청크 소유 범위 유지 |
| chunk_index | 정수 | 문서 안의 청크 순서 |
| content_hash | 정규화 본문의 SHA-256 | 내용 중복 판별 |
| is_subject | 불리언 | 종 자체 문서 우선 검색 슬롯 |
| page_number | PDF 사용 시 1부터 시작하는 파일 페이지 | 페이지 단위 출처 표시 |
| record_kind | 파생 문서일 때 ecology_fact | 원문 대조 생태 발췌의 검색 구분 |
| taxon_group, endangered_grade | 생태 파생 문서의 분류군·숫자 등급 | 조건 탐색의 생태 후보 필터 |
| modification_notice | 파생 발췌·분류 변경 고지 | 원문을 가공했다는 사실 표시 |

한 문서가 두 종과 연결되어도 종 ID가 다르면 청크 ID가 다르므로 서로 덮어쓰지 않는다. 예를 들어 `doc:sp_0001:ko-wiki-123:0`과 `doc:sp_0002:ko-wiki-123:0`은 별도 항목이다. 위 예시는 식별자 구조 설명용이며 실제 수집 결과를 뜻하지 않는다.

### 3.4 캐시와 생태 원문 기록

SQLite 캐시는 `key`, JSON `payload`, `created_at`으로 구성한다.

| 키 구분 | 저장 내용 |
|---|---|
| subject:{종ID} | 기본 수집 경로에서 성공적으로 확인한 자체 문서 후보 |
| query:{종ID}:{검색어 해시} | 선별·제외 결과와 선택 후보. 검색어는 소문자화·양끝 공백 제거 후 해시 |
| doc:{종ID}:{문서ID} | pages를 포함한 수집 본문과 원문 메타데이터 |
| ecology:v1:{종ID}:{문서ID}:{지문} | 생태 인용, 항목, 페이지 인덱스, 시점 구분, 추출 시각, 거부 기록 |
| 생태 보완 조회 키 | 한국어·영문 추가 조회와 Wikidata 학명 확인 결과 |

생태 파생 기록은 원문 인용·원문 URL·라이선스·리비전·수집 및 추출 시각을 보존한다. 파생 청크에는 원문 출처를 이어 붙이고 인용의 과거·시점 미확인 표기를 본문에 포함한다. 이 자동 대조는 인용의 존재 확인이지 전문가 사실 검증이나 현재성 보장이 아니다.

## 4 문서 수집 설계

### 4.1 기본 수집 순서

1. 선택 종과 질문을 검색어 추출 프롬프트에 전달한다.
2. 코드가 국명과 학명을 결합한 검색어를 맨 앞에 추가하고 중복을 제거한다. 기본 검색어 수는 최대 3개이다.
3. 종 자체 문서 확인 캐시를 먼저 확인한다. 없으면 한국어 위키백과에서 종명 문서와 리다이렉트를 조회한다.
4. 자체 문서는 동음이의·비문서 페이지를 제외하고 제목 일치 또는 소개문 학명 조건으로 확인한다. 선택된 자체 문서는 후보 선별·길이 제외보다 우선 수집·색인한다.
5. 검색어별 성공 캐시가 있으면 선택된 본문을 재사용한다. 없으면 위키백과 검색으로 최대 8개 후보를 받는다.
6. 제목·검색 요약·ID를 선별 프롬프트에 전달하고, 직접 관련된 후보만 선택한다. 검색어당 기본 최대 3개 문서를 수집한다.
7. 허용된 후보의 전체 본문·원문 URL·리비전·라이선스·수집 시각을 가져온다.
8. 본문을 SQLite에 먼저 저장한 다음 청킹·색인을 수행한다. 임베딩 실패가 발생해도 다음 실행에서 본문을 다시 내려받지 않는다.
9. 선택된 본문의 색인이 모두 성공한 뒤 해당 검색어를 완료 캐시로 저장한다. 검색 결과가 없는 성공 응답도 빈 결과로 캐시한다.
10. 수집 감사 정보에 검색어·선택·제외·캐시 재사용·안내를 담아 서비스에 돌려준다.

종 자체 문서가 없거나 학명이 모호할 때는 안내하고 기존 근거만 사용한다. 문서를 확보했다는 이유만으로 생태 원문 대조까지 통과한 것은 아니다. 기본 수집의 문서 식별과 생태정보 발췌의 더 엄격한 종 일치 검사를 구분한다.

### 4.2 캐시와 외부 호출 정책

성공적으로 저장한 검색 결과와 본문은 만료 없이 재사용한다. 같은 내용의 외부 청크가 이미 존재하면 저장된 ID·본문·메타데이터와 비교하여 재임베딩도 생략한다. 검색어·본문 재사용과 질문 답변 생성은 별개이므로, 캐시가 있어도 기본 수집 경로의 검색어 추출과 답변 생성에는 AI 호출이 발생할 수 있다.

실패한 요청은 완료로 표시하지 않아 재시도할 수 있다. 특히 기본 자체 문서 조회에서 찾지 못한 경우와 성공적으로 저장한 종 문서는 구분되므로 모든 종류의 실패·미확인 조회가 항상 재호출 없이 끝난다고 보장하지 않는다. 별도 생태 보완 경로는 성공한 빈 조회 결과도 전용 키에 저장한다.

기본 호출 간격은 1초이고 HTTP 제한 시간은 30초이다. 429·500·502·503·504에 대한 재시도와 Retry-After 반영을 사용한다. 위키백과 수집에는 실제 연락처가 포함된 User-Agent가 필요하다. 실값은 환경변수에 두고 제출 문서에 노출하지 않는다.

### 4.3 영문 보완과 원문 대조

한국어 자료가 짧은 종은 별도 `enrich-ecology --english-supplement` 경로로 영문 위키백과를 보완할 수 있다. 이 기능은 모든 채팅마다 자동으로 전 종의 영문 문서를 받는 기능이 아니다. 이미 저장된 본문을 우선 재사용하고 새로 필요한 문서만 수집한다.

종 자체로 확인된 문서에서 서식 환경, 국내 분포, 주요 위협 요인의 원문 문장을 추출한다. 입력 본문은 문서당 최대 30,000자로 제한하고, 규칙으로 찾은 후보 문장도 검토 힌트로 제공한다. 현재 방식은 관련 문장만 보내도록 최적화된 방식이 아니라 본문과 후보 힌트를 함께 전달하는 방식이다.

추출 후 원문 일치·페이지 인덱스·항목 표현·종 일치를 검사한다. 공백 차이 외에 문장을 고쳐 만든 인용은 허용하지 않는다. 문서별 항목당 최대 3개 인용을 채택한다. 확인되지 않는 항목은 비워 두고, 과거 기록은 historical, 나머지는 unspecified로 저장한다. 추출 결과와 원문 지문을 캐시하므로 동일 자료는 재추출하지 않는다. `--retry-rejected`, `--retry-incomplete`는 사용자가 명시하는 저장 본문 재검토이며 본문 재수집과 다르다.

### 4.4 로컬 PDF와 TXT 대체 경로

외부 API 대신 자료 묶음을 쓰는 경우 manifest에 종 ID, 문서 ID, 제목, 파일, 출처, 라이선스와 이용 조건 근거 URL을 지정한다. `license_confirmed=true`인 자료만 읽는다.

PDF는 해당 종의 파일 페이지 번호를 1부터 지정하고 `pypdf`로 텍스트를 추출한다. 전체 도감의 모든 페이지를 모든 종에 연결하지 않는다. 스캔 PDF에 텍스트가 없으면 OCR 자료가 필요하다고 안내한다. TXT는 UTF-8로 읽는다. 실제 종류가 다른 외부 자료를 결합한 F2016 검증은 별도이며, 한국어·영문 위키백과만으로 복수 유형 결합 완료라고 표시하지 않는다.

## 5 청킹과 색인 설계

### 5.1 청킹 방식과 선택 이유

`RecursiveCharacterTextSplitter`를 사용하며 길이는 토큰 수가 아니라 Python 문자열의 문자 수로 계산한다. 분리 우선순위는 빈 줄, 줄바꿈, 마침표 계열, 공백, 문자 단위이다. 문단과 문장 경계를 먼저 이용하고 길이가 넘을 때 더 작은 단위로 나누는 방식을 선택했다.

| 설정 | 기본값 | 선택 이유 |
|---|---|---|
| chunk_size | 1,000자 | 서식·분포·위협 설명에 필요한 문맥을 유지하면서 불필요한 긴 본문을 줄이는 시작값 |
| chunk_overlap | 200자 | 분할 경계에서 종명·원인·결과 문맥이 끊기는 것을 완화하기 위한 상한 |
| 길이 기준 | 문자 수 | 한국어·영문 혼합 문서에도 설정을 일관되게 적용하고 구현을 단순화 |
| PDF 단위 | 페이지별 분리 후 청킹 | 근거를 원본 PDF 페이지와 연결하고 청크의 페이지 넘김 방지 |

중복 200자는 매 청크마다 정확히 200자를 반복한다는 뜻이 아니다. 재귀 분리기가 문단 경계를 고려해 청크를 묶으므로 실제 중복량은 더 적거나 없을 수 있다. 문자 수가 같아도 토큰 수는 언어와 문장 구성에 따라 달라진다. 기본값이 품질·비용의 최적점이라고 검증된 것은 아니다.

### 5.2 색인 순서와 갱신

1. 종 메타데이터를 종당 한 문서로 만들고 고정 ID로 upsert한다.
2. 외부 문서의 pages를 순서대로 분할한다.
3. 청크 ID와 원문·종 소유 메타데이터를 붙인다.
4. 현재 저장된 동일 종·문서의 청크와 ID·본문·메타데이터를 비교한다.
5. 동일하면 기존 개수를 반환하고 재임베딩하지 않는다. 바뀌었으면 새 청크를 upsert한다.
6. 새 청크 저장 성공 후 이전 문서의 남은 청크 ID를 제거한다.

청크를 줄였을 때 예전 꼬리 청크가 남아 검색되는 문제를 방지하기 위해 새 저장 후 잔여 청크를 정리한다. 재색인은 캐시 본문을 사용하므로 외부 원문을 다시 수집할 필요가 없다. 기본 메타데이터 색인 버튼은 같은 ID로 건수 중복을 방지하지만, 누를 때 임베딩 호출 자체까지 항상 생략하는 기능은 아니다.

### 5.3 저장된 실제 본문으로 수행한 청킹 비교

2026-10-22에 기존 한국어 위키백과 산양 문서 `ko-wiki-317294`, 리비전 `42531444`의 저장 본문 2,000자를 같은 분리기로 나눴다. 아래 수치는 실제 로컬 실행 결과이며 API 호출·임베딩·운영 DB 변경 없이 계산했다.

| 청크 크기 | 중복 상한 | 청크 수 | 전체 청크 문자 합계 | 가장 긴 청크 |
|---|---|---|---|---|
| 500 | 100 | 6 | 1,989 | 487 |
| 1,000 | 0 | 3 | 1,995 | 969 |
| 1,000 | 200 | 3 | 2,010 | 969 |
| 1,500 | 300 | 2 | 2,013 | 1,354 |

이 문서에서는 청크 크기를 500자로 줄이면 6개로 세분되고, 1,500자로 늘리면 2개로 합쳐졌다. 1,000자에서 중복을 0→200으로 바꿔도 청크 수는 3개로 같았지만 포함 문자 합계는 15자 늘었다. 구분자 주변 공백 정리 때문에 중복이 없는 경우에도 원본 문자 수와 합계가 정확히 같지는 않다.

이 비교는 실제 청크 구성 차이를 보여주며 답변 정확도·임베딩 비용·검색 재현율 개선을 측정한 결과는 아니다. 긴 문서, 다른 종, PDF에서는 결과가 달라질 수 있다.

## 6 검색과 결과 병합

### 6.1 retrieve 노드

선택 종마다 아래 처리를 실행한다.

1. `metadata_for(species_id)`로 고정 ID의 메타데이터를 가져온다. 없으면 색인 안내 후 중단한다.
2. 국명과 질문을 결합하여 외부 문서를 검색한다. Chroma 필터에 종 ID를 지정한다.
3. 기본 similarity 검색으로 Top-k개를 가져온다. 설정이 mmr이면 MMR 검색을 실행한다.
4. 질문에 여러 생태 항목이 있으면 항목명별 유사도 검색 결과를 추가해 특정 주제로만 쏠리는 것을 완화한다.
5. 요청 항목의 접두어가 있는 ecology_fact 청크를 가져와 해당 항목 포함 개수 순으로 우선 배치한다.
6. 종 자체 문서의 청크가 있으면 외부 근거의 첫 슬롯에 하나를 우선 배치한다.
7. 중복 청크를 정리하고 최종 외부 결과를 Top-k로 제한한다.
8. 메타데이터와 외부 결과를 합친 뒤 `merge_evidence()`로 중복을 제거하고 근거 번호를 부여한다.

이 검색은 순수 유사도 순위만 사용하는 방식이 아니다. 자체 문서 슬롯과 생태 발췌 우선순위가 함께 적용된다. MMR을 선택하더라도 이후의 보강·슬롯 규칙이 적용되므로 최종 결과를 그대로 순수 MMR 결과라고 해석하지 않는다.

### 6.2 중복 제거와 종 소유 관계

| 단계 | 중복 기준 | 처리 |
|---|---|---|
| 외부 후보 병합 | chunk_id | 같은 청크를 여러 검색에서 찾으면 먼저 나온 것만 유지 |
| 최종 근거 병합 | chunk_id 또는 종 ID와 정규화 본문 해시 | 동일 종의 같은 내용은 한 번만 포함 |
| 비교 질문 | 종 ID가 다르면 별도 소유로 유지 | 같은 출처·본문이어도 두 종의 연결 관계를 임의로 없애지 않음 |

본문 해시는 Unicode NFKC 정규화와 연속 공백 축약 후 SHA-256으로 만든다. 서로 비슷하지만 문장이 다른 청크를 의미적으로 합치는 방식은 아니다. 중복 제거 후 순서대로 1부터 `evidence_id`를 부여한다.

메타데이터를 벡터 유사도에 맡기지 않고 강제 포함한 이유는 선택 종의 기본 사실을 잃지 않기 위해서다. 종 ID 필터는 다른 종의 문서가 현재 질문 근거에 섞이는 것을 막는다.

## 7 프롬프트 역할과 출력 형식

### 7.1 기본 프롬프트 3개

| 구분 | 역할과 입력 | 출력 형식 | 제어와 선택 이유 |
|---|---|---|---|
| 검색어 추출 QUERY | 생물 문헌 검색 전문가. 종의 기본 텍스트와 질문 입력 | queries 문자열 배열 | 질문을 외부 문서 검색에 적합한 단위로 바꾸고 국명·학명을 함께 활용한다. 코드에서도 자체 문서 검색어를 보완한다. |
| 후보 선별 SELECT | 생물다양성 문헌 검토자. 종·질문·후보 ID·제목·요약 입력 | decisions 배열의 document_id, selected, reason | 전체 본문을 받기 전에 무관 후보를 버려 호출·색인량을 줄인다. 주어진 후보 ID만 허용한다. 자체 문서는 이 선별보다 우선한다. |
| 답변 생성 ANSWER | 생태 지식 안내자. 질문·최근 대화·번호가 붙은 근거 입력 | answer 문자열, used_evidence_ids 정수 배열 | 근거 범위에서 한국어로 설명하고 주요 주장에 번호를 붙인다. 자료 부족·과거 기록·국내외 범위를 구분한다. |

다음 JSON은 필드 구조 예시이며 실제 모델 실행 결과를 인용한 것은 아니다.

```json
{"queries":["산양 Naemorhedus caudatus","산양 서식지 위협"]}
```

```json
{"decisions":[{"document_id":"ko-wiki-123","selected":true,"reason":"선택 종의 서식 환경을 설명함"}]}
```

```json
{"answer":"제공된 근거에서 확인한 설명입니다. [근거 1]","used_evidence_ids":[1]}
```

프롬프트를 나눈 이유는 검색어 계획, 후보 판단, 최종 설명이 서로 다른 책임이기 때문이다. 선별 실패가 본문 수집 실패와 섞이지 않고 각 단계의 결과를 확인할 수 있다. 문서와 대화에 들어 있는 지시문은 데이터로 취급하고 따르지 않도록 명시했다.

### 7.2 형식 검증

`response_format=json_schema`와 strict JSON Schema를 사용한다. 필요한 필드는 required로 지정하고 임의 추가 필드는 허용하지 않는다. JSON 파싱에 실패하면 형식 수정 요청을 포함하여 한 번 더 호출한다. 그 후에도 객체로 처리하지 못하면 사용자용 오류를 반환한다.

JSON Schema는 구조를 제한하지만 사실 정확성이나 관련성을 보장하지 않는다. 후보 ID가 입력 후보에 있는지, 인용 번호가 실제 근거에 있는지 등은 코드로 다시 검사한다.

### 7.3 generate 노드와 추가 프롬프트

근거 번호는 유지한 채 생성 문맥의 제시 순서를 생태 발췌, 일반 외부 문서, 메타데이터 순으로 조정한다. 기본 목록의 빈 속성 때문에 외부 생태정보까지 무시하는 현상을 완화하기 위한 결정이다. 대화는 최근 6개 메시지만 제공한다. 과거 답변은 문맥으로 사용하되 사실 근거는 이번에 전달한 자료로 제한한다.

| 추가 프롬프트 | 목적 | 출력 |
|---|---|---|
| EXPLORE | 조건과 후보 메타데이터·출처 연결 생태정보를 읽고 모든 조건을 만족하는 종만 선별 | matches의 species_id, reason |
| ECOLOGY | 같은 종의 원문에서 항목별 인용을 그대로 발췌. 정보가 없으면 빈 배열 | claims의 field, quote, page_index, time_scope |

추가 프롬프트는 서비스 확장을 위한 것으로 명세서의 기본 3개 역할을 대체하지 않는다.

## 8 검색 설정과 값 변경 영향

### 8.1 적용 설정과 근거

| 설정 | 현재 값 | 선택 이유 |
|---|---|---|
| top_k | 외부 청크 종당 4개 | 자체 문서와 여러 생태 항목 근거를 함께 담고 과도한 문맥을 제한하기 위한 시작값 |
| search_type | similarity | 관련성 중심의 기본 경로를 먼저 확인하고 MMR과 비교할 기준으로 사용 |
| mmr_fetch_k | 20 | 최종 4개보다 넓은 후보에서 다양성을 선택할 여유 확보 |
| mmr_lambda | 0.5 | 관련성과 다양성 사이의 중간 설정으로 출발 |
| catalog_candidates | 컬렉션별 20개 | 자연어 탐색에서 LLM이 검토할 후보량 제한 |
| max_queries | 3 | 자체 문서 검색과 추가 검색의 호출량 제한 |
| max_documents_per_query | 3 | 무분별한 본문 수집·색인 방지 |

자연어 탐색은 메타데이터 후보와 생태 발췌 후보를 종 ID로 합치므로 최종 검토 종 수가 항상 20개 이하인 것은 아니다. 후보 밖의 종은 선별할 수 없어 전수 탐색을 보장하지 않는다.

### 8.2 Top-k 변경 시 구조상 차이

| 외부 Top-k | 한 종 근거 상한 | 두 종 근거 상한 | 예상 영향 |
|---|---|---|---|
| 2 | 3 | 6 | 짧은 문맥이지만 서식·분포·위협을 동시에 담기 어려울 수 있음 |
| 4 | 5 | 10 | 현재 기준. 자체 문서와 항목별 근거를 함께 담기 위한 절충 |
| 6 | 7 | 14 | 근거 폭이 넓어질 수 있으나 중복·무관 문맥과 입력량이 증가할 수 있음 |

상한은 종당 메타데이터 1개를 포함해 계산한 구조적 값이며 실제 동일 질문 실측 결과가 아니다. 문서 부족·중복 제거 때문에 실제 근거 수는 더 작을 수 있다. Top-k가 커진다고 정답률이 반드시 높아지지는 않는다. 외부 검색이 여러 보강 경로를 실행해도 반환하는 외부 근거 수는 마지막에 Top-k로 제한한다.

### 8.3 MMR의 적용 범위와 남은 비교

MMR은 질문과의 관련성과 이미 선택한 문서와의 차이를 함께 고려한다. 비슷한 설명이 반복되는 청크가 근거를 독점하는 것을 줄이기 위해 선택 옵션으로 구현했다. 실제 Chroma MMR 실행과 결과 수 제한은 자동 테스트로 확인했으나 동일 질문에 대한 similarity·MMR 근거 목록의 최종 제출용 비교는 아직 추가로 정리해야 한다.

F2014 검증에서는 같은 원문·질문·Top-k를 고정하고 기본 검색 방식만 바꿔 근거 ID, 제목, 내용 중복, 항목 커버리지를 비교한다. F2015는 대표 질문 5개 이상에 대한 RAG 전후 답변을 비교하는 별도 과제로, 설정이 존재한다는 이유만으로 평가 완료라고 표시하지 않는다.

## 9 답변과 근거 표시

### 9.1 번호 부여와 검증

검색된 근거는 `[근거 N]` 형식으로 생성 모델에 전달한다. 각 근거에는 종 ID·문서 제목·출처 유형·본문이 들어간다. 모델에는 주요 주장 바로 뒤에 근거 번호를 넣도록 요청한다.

코드는 응답의 `used_evidence_ids`만 믿지 않고 답변 본문에서 `\[근거\s*(\d+)\]` 형식의 번호를 찾는다. 제공하지 않은 번호가 있으면 수정 요청 후 다시 생성한다. 근거 없는 사실 답변도 보정 대상으로 처리한다. 근거가 없다는 취지의 응답은 별도 안내와 함께 허용한다. 보정 후에도 인용 검증에 실패하면 사용자용 오류를 표시한다.

이 검사는 인용 번호의 존재·유효성을 검사한다. 모든 문장이 실제로 해당 근거에서 도출되는지까지 자동으로 증명하는 의미적 검증기는 아니다. 미확인 응답 판별도 표현 규칙이므로 사람의 품질 검토가 필요하다.

### 9.2 사용자에게 표시하는 정보

- 답변 본문의 근거 번호
- 본문에서 실제 인용한 근거만 모은 펼치기 영역
- 문서 제목과 메타데이터·외부 문서 유형
- 원문 URL, 라이선스, 문서 리비전
- 로컬 자료의 파일명과 PDF 페이지
- 생태 파생 문서의 발췌·분류 변경 고지
- 해당 근거 청크의 본문과 전체 처리 시간

인용이 없으면 인용 근거가 없다는 안내를 표시한다. 검색 과정에서 받았지만 사용하지 않은 문서를 답변의 사용 근거로 전부 나열하지 않는다. 다크모드에서도 진행 표시줄·펼치기 제목·원문 텍스트에 별도 색상을 적용해 근거 확인을 방해하지 않도록 했다.

## 10 도메인 특화 기능과 설계 이유

### 10.1 두 종 생태 비교

핵심 특화 기능은 두 종의 서식 환경·국내 분포·주요 위협 요인을 근거와 함께 비교하는 것이다. 서로 다른 종의 생태적 차이를 같은 항목으로 살펴보는 기능이 백과 도메인에 적합하며, 근거가 없으면 틀리기 쉬운 비교 질문을 제공한다.

첫 번째와 두 번째 종 선택 영역을 분리하여 각각 이름·분류군·등급으로 찾게 했다. 두 번째 후보에서 첫 번째 종을 제외하고, 두 종이 모두 선택되었을 때만 실행한다. 동일한 RAG 그래프에 두 종 ID를 전달하되 각 종의 메타데이터와 외부 검색을 독립 수행한다. 최종 비교 표의 각 항목에 해당 종 근거를 인용하도록 프롬프트에서 지시한다.

원본 속성이 없다는 이유만으로 표 전체를 비우지 않고 외부 근거를 확인한다. 반대로 한 종에만 근거가 있을 때 다른 종의 내용으로 채우지 않는다. 정확한 현행 분포나 최신 개체수 비교를 보장하는 기능은 아니다.

### 10.2 자연어 조건 탐색

‘2급 포유류’, ‘산림에 서식하는 1급 포유류’ 같은 조건을 별도 페이지에서 받는다. 선택 종에 종속된 검색으로 오해하지 않도록 종별 대화와 화면을 분리했다.

입력을 정규화한 뒤 분명한 등급·분류군 조건을 Chroma 필터로 적용한다. 메타데이터와 ecology_fact 후보를 검색하여 종 ID로 합치고, 출처가 연결된 생태 문장과 함께 EXPLORE에 전달한다. 후보 목록에 없는 ID와 중복 ID는 제거한다. 결과 카드를 누르면 해당 종 질문으로 이동하고 이전 필터가 새 선택을 덮어쓰지 않도록 초기화한다.

등급과 분류군 키워드 버튼은 입력을 돕는 기능이며 선택만으로 AI를 호출하지 않는다. 생태 조건은 자료를 확보한 종에서만 판단하므로 결과가 없는 것이 실제 생물학적 부재를 뜻하지 않는다.

### 10.3 정보 확보 상태와 추천 질문

정보 확보 상태는 메타데이터 값, 원문 대조 인용, 관련 표현, 미확보를 구분한다. 이 화면 계산 자체는 로컬 캐시만 읽는다. 추천 질문은 기본 정보·특징 요약과 관련 근거가 있는 생태 항목을 제안하고 버튼을 누르면 입력창만 채운다. 사용자가 전송하기 전에는 수집·AI 답변을 실행하지 않아 의도하지 않은 토큰 사용을 줄인다.

대표 사진은 종 식별을 돕는 별도 화면 기능이다. 사진을 벡터 색인하거나 생태 답변의 텍스트 근거로 사용하지 않는다.

## 12 검증 현황과 재현

### 12.1 확인된 내용

- 자동 테스트 79개 통과 이력: 항목 로드, 중복 방지, Chroma 검색·MMR, 종별 격리, 캐시 재사용, 인용 검증, 생태 발췌, Streamlit 화면 등을 포함한다.
- 실제 GMS gpt-5.4-mini 구조화 JSON 응답을 확인했다. 모델 변경 전의 생태 질의·비교 검증과 최신 모델의 전체 품질 재평가는 구분한다.
- 대표 20종에서 원문 대조 인용 90건을 확보했다. 60개 항목 중 원문 대조 48개이며 모두 최신 사실로 검증된 것은 아니다.
- 처리된 20종을 같은 내용으로 다시 실행할 때 HTTP·AI 재추출·재임베딩을 금지한 상태에서 저장 결과 재사용을 확인했다.
- 저장된 실제 산양 문서로 청크 크기·중복 변경에 따른 청크 수와 문자 합계를 로컬 비교했다.
- 실제 다크모드 질문 처리 표시줄과 답변 근거 원문을 확인했다.

자동 테스트의 LLM·임베딩 대역 검증과 실제 API 실행 결과는 구분한다. 모든 종의 답변 정확도, 동일 질문 Top-k 비교, similarity·MMR 최종 품질 비교, 대표 5개 이상의 RAG 전후 평가, 권리 확인된 복수 유형 자료 결합은 추가 검증이 필요하다.

### 12.2 재현 명령

프로젝트 폴더에서 실행한다. API를 쓰는 명령에는 비용이 발생할 수 있으므로 목적에 맞는 명령만 실행한다.

```powershell
# 기본 데이터와 그래프 구조 확인
.\venv\Scripts\python.exe -m ecopedia.cli check-data
.\venv\Scripts\python.exe -m ecopedia.cli graph

# 자동 테스트
.\venv\Scripts\python.exe -m unittest discover -s tests -q

# 메타데이터 임베딩. API 비용 발생 가능
.\venv\Scripts\python.exe -m ecopedia.cli index-metadata

# 청킹 설정 변경 후 캐시 본문 재색인. 임베딩 비용 발생 가능
.\venv\Scripts\python.exe -m ecopedia.cli reindex-documents

# 대표 20종 보강. 수집·AI·임베딩 비용 발생 가능
.\venv\Scripts\python.exe -m ecopedia.cli enrich-ecology --collect-missing --english-supplement --limit 20

# 별도 RAG 전후 답변 확보. 실제 API 비용 발생, 사람 평가 필요
.\venv\Scripts\python.exe -m ecopedia.cli compare-rag data/evaluation-questions.json
```

설정 비교는 운영 캐시를 삭제하지 않고 수행한다. 청크 변경 후에는 저장 본문으로 재색인하고, 끝난 뒤 비교용 설정과 기본 설정을 구분해 기록한다. 향후 성능 비교에서는 동일 원문 리비전·질문·모델·설정을 고정하고 근거 ID와 사용 문맥, 처리 시간, 평가 결과를 함께 남긴다.
